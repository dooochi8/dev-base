# verify

実行結果だけを根拠に報告する。実行していないことを確認済みと言わない。

## 基本姿勢

- 実行した出力だけを根拠に報告する。実行していないことを確認済みと言わない。
- 振る舞いの確認が完了条件であり、コードを読んだだけでは完了ではない。
- 検証できなかった項目は「検証できなかった理由」とともに明示する。

## ガードレール

- テストを通すためにテスト自体を弱める・スキップしない。
- 失敗した出力を加工・省略して報告しない。
- 「おそらく動く」「問題ないはず」という表現で完了を主張しない。
- 検証の対象と無関係なコードをこの段階で変更しない。

## 進め方

1. **検証すべき振る舞いを列挙する**
   - 今回の変更が「何を変えた」かを、観測可能な振る舞いとして書き出す。
   - 変更に隣接する既存の振る舞いも対象に含める。

2. **検証手段を特定する**
   - テスト（ユニット・統合・E2E）
   - 型チェック（`tsc --noEmit` 等）
   - lint / formatter
   - 実際の起動・実行（`npm run dev`、`curl` 等）
   - 手動確認が必要な場合はその手順を明示する。

3. **実行する**
   - 特定した手段を順に実行する。
   - 出力を切り取らず、失敗があれば全文を保持する。

4. **出力と期待を照合する**
   - 期待される出力と実際の出力を並べて比較する。
   - 差分があれば原因を特定するまで完了としない。

5. **報告する**
   - 下記フォーマットに従って報告する。

## 報告フォーマット

```
## 実行したコマンド
<コマンドを列挙>

## 結果
| 振る舞い | 検証手段 | 結果 | 要点 |
|---------|---------|------|------|
| ...     | ...     | ✅/❌ | ... |

## 検証できなかったこと
| 項目 | 理由 |
|------|------|
| ...  | ...  |
```

- 結果が ❌ のときは、出力の要点を引用して原因を示す。
- 「検証できなかったこと」が存在する場合は必ず記載する。存在しない場合は「なし」と書く。

## 実務上の判断

- テストがないコードベースでは、実際に起動して主要な経路を手動確認する。その手順と結果を報告フォーマットに含める。
- flaky なテストに遭遇したら、スキップではなく「不安定なテストがある」と明示してブロックを上げる。
- 環境固有の検証（認証・外部 API）が必要な場合は、モックで代替できるか判断し、できない場合は検証不能として理由を書く。

## 完了条件

- すべての主要な振る舞いについて、実行結果による根拠がある。
- 検証できなかった項目は、検証不能の理由とともに明示されている。
- 失敗した検証がある場合は、原因が説明されている。
