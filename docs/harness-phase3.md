# ハーネス段階3：自動化の設計

[ハーネス設計](harness.md) の段階3（クラウドエージェントでの並列実行、ファジング、自動マージ）の前提条件と進め方。段階3は人間の確認を減らす変更であり、内側のループ（段階1・2）が信頼できる時だけ利益になる。検証の弱いまま並列化すると、slop が並列に増える。

この文書は設計であり、dev-base も複製先も、ここに書いた自動化を既定では有効にしない。各段は、対象リポジトリの所有者が前提条件を確かめて有効にする。

## 前提条件（段階3へ入る判断）

すべてを満たし、根拠を `docs/verification.md` に記録してから始める。

| 前提 | 確かめ方 |
|---|---|
| 段階1の検査が CI で必須になっている | `harness-check`・型・lint・テストが PR の必須チェックで、`--self-test` が通る |
| baseline が縮み続けている | 直近の期間に `harness-baseline.json` の件数が増えていない |
| 段階2の完了条件を満たしている | [段階2の完了条件](harness.md#段階2の完了条件) を満たしている |
| 検証が決定論的である | 必須チェックの不安定な失敗（再実行で通る失敗）が直近で起きていない。起きたら原因を直してから進む |
| エージェントのPRが人間のレビューで大きく直されていない | 直近のエージェントPRで、レビュー指摘の多くが `mistake-to-rule` で仕組みに変わっている |
| 秘密情報と権限が分かれている | クラウドの実行環境に本番の認証情報がない。必要な鍵は環境の機能で最小範囲に渡す |

## 段階3a：クラウドエージェントでの並列実行

独立した作業を複数のクラウドセッションへ分け、各成果を段階2の検証で確かめる。

- **単位**: Linear の Issue 1件 = ブランチ1本 = PR1件。共有する書込（同じファイル、同じ設定、DBのマイグレーション）がある作業は並列にせず、順に行う（`principle-separate-before-serializing-shared-state`）。
- **入力**: 各セッションへ、Issue、`plan-handoff` 形式の実行指示書、触らないもの、完了条件、検証コマンドを渡す。モデルはセッションの設定を継承し、禁止族を model 引数に渡さない。
- **出力**: 各PRは `templates/harness/pr-evidence.md` の証拠を持つ。証拠のないPRはレビュー待ちにしない。
- **統合**: 主担当は各PRの差分と証拠を自分で確認し、`interrogate` 等の独立レビューを通す。統合順は依存関係で決める。
- **止める条件**: 同じ種類のレビュー指摘が複数のPRで出たら、並列を止めて `mistake-to-rule` でルールにしてから再開する。

使う手順は pstack の `swarm`、`orchestrate`、`autopilot-*` の playbook。上流の bun・gh・gt 依存と、未検証の長時間実行（[採用範囲](pstack-adoption.md)）を確かめてから使う。

## 段階3b：ファジングと修正PR

リリース候補ごとに、入力と操作列を生成してアプリを壊しにいき、見つけた失敗を再現テスト付きの修正PRにする。

1. **対象を決める**: 外部入力の境界（パーサ、API、ファイル読み込み）、状態遷移図のある重要フロー、モデル検査の判断基準に当たるフロー。
2. **生成する**: 境界はプロパティベーステストの生成器を長く回す。フローは機能マップと検証用CLIを使い、ランダムな操作列を実アプリへ与える。乱数のシードと実行時間を記録する。
3. **縮める**: 失敗した入力を最小例へ縮め、決定論的な回帰テストにする。
4. **直す**: 1件の失敗につき1件の Issue と PR。修正は `bug-fix` の playbook に従い、再現テストが修正前に失敗し、修正後に通ることを証拠に載せる。
5. **記録する**: 見つからなかった範囲（時間・シード・対象外のフロー）も記録する。見つからないことを、壊れないことの証明として扱わない。

ファジングは CI の必須チェックにしない。時間で打ち切る探索は結果が決定論的でないため、定期実行（リリース候補ごと、または夜間）で回し、見つけた最小例だけを必須の回帰テストへ移す。

## 段階3c：自動マージ（既定で無効）

強い検証を通った低リスクの変更だけを、人間の承認なしにマージする。各リポジトリの既存の承認条件を変える判断であり、所有者が明示的に有効にするまで使わない。dev-base と `project-start` の複製は、自動マージの設定・ワークフロー・ブランチ保護の変更を含まない。

### 有効にする条件

- 段階3aと3bを一定期間運用し、エージェントのPRが人間のレビューで直されることがまれになっている。
- 自動マージ後の問題を検出し、戻す手段がある（監視、`git revert` の手順、機能フラグ）。
- 所有者が、対象の範囲と期限を文書で決めている。

### 対象にしてよい変更

- 変更が、決めた範囲（例: 依存の patch 更新、文書、機能フラグで隠れた新機能）に収まる。
- 段階1・2の必須チェックがすべて通り、`harness-baseline.json` の件数が増えていない。
- PRに機能IDごとの振る舞いの証拠があり、検証できなかった項目がない。
- 独立レビュー（別のエージェントの実行）が指摘なしで終わっている。同じモデルの別実行を、人間のレビューの代わりとは扱わない。

### 常に対象外

- 認証・権限・課金・個人情報・データの削除やマイグレーション。
- CI、ブランチ保護、`harness.config.json`、`harness-baseline.json`、AGENTS.md、スキル、この文書など、検査そのものを変える変更。
- 元に戻せない外部操作（送信、公開、デプロイの設定変更）を含む変更。

上流 pstack の playbook にある自動マージの例を、この設定の許可と解釈しない（[実行対応](../poteto-mode/references/runtime.md)）。

## 段階の進め方

| 段 | 始める条件 | 失敗した時に戻る先 |
|---|---|---|
| 3a 並列実行 | 前提条件をすべて満たす | 並列を止め、指摘をルールにする |
| 3b ファジング | 3aが安定し、状態遷移図と検証用CLIがある | 見つけた失敗を直すまで新しい対象を足さない |
| 3c 自動マージ | 3a・3bの運用実績と、所有者の明示的な決定 | 自動マージを無効にし、人間のレビューへ戻す |

各段の開始と停止は、Linear の Issue と `docs/verification.md` に理由と根拠を残す。
