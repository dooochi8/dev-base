# T1: 新規スキル5本の作成指示

## 共通要件

- 各スキルはトップレベルの `<skill-name>/SKILL.md` と `<skill-name>/agents/openai.yaml` を作成する。`.claude/skills/` には書かない（sync スクリプトで生成するため）。
- すべて日本語。語彙・文体は既存スキル（`dev-base/SKILL.md`、`tdd/SKILL.md` など）に揃える。
- frontmatter は `name` と `description` のみ。description は「〜したいときに使う」が含まれる、起動判断できる一文〜二文。
- 節構成: ガードレール（または基本姿勢）を冒頭付近に置く → 進め方（番号付き）→ 出力フォーマット（必要なら）→ 完了条件。
- 長さの目安: 各 SKILL.md は 60〜120 行。巨大化させない。
- `agents/openai.yaml` は既存（`dev-base/agents/openai.yaml`）と同形式: `interface.display_name` / `short_description` / `default_prompt`。

## 1. verify

目的: 変更後に実際に動かして確認する完了ゲート。軽量モデルの「未検証の完了宣言」を構造で防ぐ。

必ず含める内容:

- 基本姿勢: 「実行した出力だけを根拠に報告する。実行していないことを確認済みと言わない」
- ガードレール:
  - テストを通すためにテスト自体を弱めない・スキップしない
  - 失敗した出力を加工・省略して報告しない
  - 「おそらく動く」「問題ないはず」という表現で完了を主張しない
- 進め方: 検証すべき振る舞いを列挙 → 検証手段を特定（テスト / 型チェック / lint / 実際の起動・実行）→ 実行 → 出力と期待の照合 → 報告
- 報告フォーマット: 実行したコマンド / 結果（成功・失敗、要点の出力引用）/ 検証できなかったことと理由
- 完了条件: すべての主要な振る舞いについて、実行結果による根拠があるか、検証不能と明示されている

## 2. plan-handoff

目的: 計画者（高性能モデルや人間）が、実行者（軽量モデル）に渡す実行指示書を書く。実行者が再解釈せずに進められる粒度にする。

必ず含める内容:

- 原則: 実行者は指示書だけを見て作業する前提で書く。曖昧語（「適切に」「いい感じに」「必要に応じて」）を避ける。検証コマンドは実在を確認したものだけ書く。
- 実行指示書テンプレート:
  ```md
  ## 目的
  この作業で実現する観測可能な振る舞い。

  ## 触るファイル
  変更が想定されるファイルと、それぞれで何をするか。

  ## 触らないもの・禁止事項
  - リファクタしてはいけない箇所
  - 追加してはいけない依存・抽象
  - スコープ外の変更

  ## 手順（縦切り）
  1. 最初に通す tracer bullet
  2. 以降のスライス

  ## 受け入れ条件
  - [ ] 条件（観測可能な形で）

  ## 検証コマンド
  実行者が完了前に必ず実行するコマンド。

  ## 報告フォーマット
  変えたもの / 実行した検証と出力 / 未確定・未検証のこと
  ```
- 完了条件: 実行者が質問なしで着手でき、完了判定が機械的にできる状態

## 3. orient

目的: 未知のリポジトリを最短で把握し、以降の作業の土台になるマップを作る。

必ず含める内容:

- 基本姿勢: 全部読まない。入口と主要経路1本を優先する。把握に時間を使いすぎない。
- 進め方: README・設定ファイル（package.json 等）→ エントリポイント特定 → 代表的な1機能の経路をトレース → テストの配置と実行方法 → 規約（lint / format / ディレクトリ構成の慣習）
- 出力フォーマット（マップ）: 技術スタック / ディレクトリ構成の要点 / エントリポイント / 代表的な処理経路 / テストの場所と実行コマンド / 規約 / まだ分かっていないこと
- ガードレール: マップ作成段階でコードを変更しない。推測で書いた項目は推測と明示する。

## 4. debug

目的: 当てずっぽうの修正を繰り返さず、系統的に原因を特定して直す。

必ず含める内容:

- ガードレール:
  - 再現できていない段階で修正を始めない
  - 一度に複数の変更を入れて試さない
  - 観測した事実と仮説を区別して記録する
- 進め方: 再現手順の確立 → 再現の最小化 → 仮説を複数列挙 → 切り分け（二分探索・ログ・デバッガ）で仮説を棄却 → 原因特定 → 失敗テストで固定（可能なら）→ 修正 → verify
- 実務上の判断: 直せたが原因を説明できない場合は完了としない。タイミング依存・環境依存の兆候があれば早めに明示する。
- 完了条件: 原因が説明できる / 再現ケースが修正後に通る / 関連テストが緑

## 5. review-diff

目的: 目の前の差分を、完了前にバグと単純化の観点でレビューする。

必ず含める内容:

- 基本姿勢: 「動くか」ではなく「どんな条件で壊れるか」を探す。
- レビュー観点:
  - 正しさ: エッジケース、エラー処理、境界値、並行性
  - 要件との一致: 受け入れ条件を本当に満たしているか
  - 単純化: 不要な抽象、dead code、既存ユーティリティの再発明
  - テスト: 振る舞いを検証しているか、実装詳細に依存していないか
- 出力フォーマット: 指摘ごとに 重要度（high / medium / low）/ 場所 / 何が問題か / 提案
- ガードレール: スコープ外の設計改善は指摘リストに混ぜず、`improve-codebase-architecture` 行きとして分けて書く。指摘ゼロのときは「確認した観点」を列挙する。

- [ ] 語彙が既存スキルと揃っている（縦切り / tracer bullet / 振る舞い / 観測可能）
- [ ] `.claude/skills/` には手で書いていない
