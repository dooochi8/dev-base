# ワークフロー: スキルの連鎖パターン

スキルを単独で使うだけでなく、複数を連鎖させることで「計画→実装→検証→レビュー」のサイクルを効率的に回せます。
以下に規模別の3パターンを示します。

---

## パターン1: 小さな修正

**場面**: 既知のリポジトリで、スコープが明確な小さな変更（バグ修正・設定変更・ドキュメント修正など）。

```
dev-base → verify → (必要なら) review-diff
```

| ステップ | スキル | やること | 次へ渡すもの |
|---------|--------|----------|------------|
| 1 | `dev-base` | コードベースを探索し、最小の縦切りで実装する | 変更済みのコード差分 |
| 2 | `verify` | 変更後の振る舞いをテスト・型・lint・手動確認で検証する | 検証レポート（実行コマンドと結果） |
| 3 | `review-diff` | 差分をレビューし、バグ・単純化の観点で指摘する（変更が小さく自信があれば省略可） | レビュー指摘リスト（または「指摘なし」と確認した観点） |

---

## パターン2: バグ修正

**場面**: 再現手順が曖昧、または原因が不明なバグ。当てずっぽうの修正を繰り返さず、系統的に原因を特定したい。

```
debug → (再現テストの固定) tdd → verify
```

| ステップ | スキル | やること | 次へ渡すもの |
|---------|--------|----------|------------|
| 1 | `debug` | 再現手順を確立し、最小ケースに絞り、仮説を立てて切り分け、原因を特定する | 「○○が原因だったから○○という振る舞いが起きた」という説明と再現ケース |
| 2 | `tdd` | 特定した原因を再現する失敗テストを書き（red）、最小の修正で緑にする（green）、必要ならリファクタ（refactor） | 緑のテストと修正コード |
| 3 | `verify` | テスト・型・lint を実行し、修正後の振る舞いを根拠づける | 検証レポート |

**注意**: `debug` のステップ6で失敗テストを書ける場合は、`tdd` に移行せず `debug` の中で固定してもよい。

---

## パターン3: 中規模以上の機能開発

**場面**: 要件が曖昧、複数ファイルにまたがる実装、または未知のリポジトリへの機能追加。
計画と実装を同じ環境で進めてもよい。実際に担当を分ける時だけplan-handoffで引き継ぐ。以下は分業する場合の例。

### 計画側の作業

```
(未知のリポなら) orient → grill-me → write-a-prd → prd-to-issues → plan-handoff
```

| ステップ | スキル | やること | 次へ渡すもの |
|---------|--------|----------|------------|
| 1 | `orient` | リポジトリの技術スタック・エントリポイント・主要経路をマップ化する（未知のリポ初回のみ） | リポジトリマップ（技術スタック・処理経路・規約） |
| 2 | `grill-me` | 設計案・要件の前提を一問ずつ詰め、未解決の分岐をなくす | 確定した前提と判断ログ |
| 3 | `write-a-prd` | 問題・解決方針・ユーザーストーリー・実装判断・テスト方針・スコープ外を記した PRD を作る | PRD ドキュメント |
| 4 | `prd-to-issues` | PRD を薄い縦切りの issue 群に分解し、依存関係と受け入れ条件を整理する | issue 群（各 issue に受け入れ条件・ブロッカーあり） |
| 5 | `plan-handoff` | issue ごとに「触るファイル・禁止事項・手順・受け入れ条件・検証コマンド」を明記した実行指示書を作る | 実行指示書（実行者が質問なしで着手できる粒度） |

### 実行側の作業

```
(実行指示書を受けて) dev-base / tdd → verify → 報告
```

| ステップ | スキル | やること | 次へ渡すもの |
|---------|--------|----------|------------|
| 6 | `dev-base` または `tdd` | 実行指示書に従い、最小の縦切りで実装する。振る舞いを定義できるなら `tdd` で進める | 変更済みのコード差分 |
| 7 | `verify` | 実行指示書の「検証コマンド」と受け入れ条件を実行し、出力を根拠に検証する | 検証レポート（実行コマンドと全結果） |
| 8 | 報告 | 変えたもの・実行した検証と出力・未確定・未検証のことを計画側に伝える | 実装完了報告 |

### 計画側によるレビュー・再指示

```
review-diff → (必要なら) plan-handoff で修正指示を再度渡す
```

| ステップ | スキル | やること | 次へ渡すもの |
|---------|--------|----------|------------|
| 9 | `review-diff` | 実行側が出した差分をレビューし、バグ・単純化の観点で指摘をまとめる | レビュー指摘リスト |
| 10 | `plan-handoff` | 指摘を修正指示書として実行者に渡す（問題なければスキップ） | 修正実行指示書 |

---

## スキルとライフサイクルの対応

```
把握      orient
要件      grill-me → write-a-prd
分解      prd-to-issues
受け渡し  plan-handoff
実装      dev-base / tdd / debug
確認      verify / review-diff
設計改善  improve-codebase-architecture
```

`improve-codebase-architecture` は上記パターンには含まれませんが、`review-diff` でスコープ外と判定された設計摩擦や、機能開発サイクルの合間に使います。

## 共通の開発管理と補助スキル

- 新しいプロジェクトの環境一式を作る時は `project-start`。既存要件を引き継ぎ、dev-base・GitHub・Linear・共通スキルの準備を済ませてから本機能の開発へ進む。
- PRDや計画の草案を確認する時は、技術的な実現性・データ・エラー処理に `plan-eng-review`、画面・導線・表示状態に `plan-design-review` を選ぶ。必要な観点だけ確認し、レビュー依頼では実装・仕様変更を始めない。
- Issueと実装の対応は `linear-workflow` を使う。変更の入口と終了時の読み戻しを管理し、仕様はdocs、差分はGitHub PRへ結ぶ。
- `grill-me` は一問ずつ、`grilling` は独立した質問をラウンドで扱う。同じ確認を両方で繰り返さない。
- 処理順・責任・UIの比較が文章だけでは分かりにくい時に `show-me` を使う。単純な説明に図を強制しない。
- コードを根拠に構成・主要フロー・開発ガイドを文書として保存する時は `smart-docs` を使う。素早い把握は `orient`、一つの関係の図解は `show-me` に留め、文書化で実装変更まで行わない。
- 利用者向けUIの見た目・操作感・動きを磨く時は `emil-design-eng` を使う。動かさない判断、reduced-motion、タッチ・キーボード、負荷下の性能を含めて確認し、導入だけでUI変更や依存追加は行わない。
- SkillやAGENTSの指示を独立実行で評価したい時に `empirical-prompt-tuning` を使う。利用可能な実行環境を確認し、自己再読を独立評価と呼ばない。
- スキル導入依頼は、そのスキルの対話・反復評価の開始指示ではない。必要な作業を選択する。
