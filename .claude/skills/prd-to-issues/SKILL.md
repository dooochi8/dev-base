# PRD To Issues

PRD を、独立して進めやすい実装 issue 群に分解する。

## 進め方

1. 対象の PRD を読む。
2. 必要ならコードベースを探索し、現状との差分を把握する。
3. PRD を薄い縦切りへ分解する。
4. 各スライスの依存関係と完了条件を整理する。
5. 承認済みの要件・依頼範囲で粒度と依存関係を決め、結果を変える未確定判断だけユーザーへ確認する。
6. Issue形式でまとめる。起票まで依頼されていれば `linear-workflow` に従って既存Issueを確認してから登録する。分解案だけの依頼なら外部起票しない。

## 原則

- 横切りではなく縦切りで分解する。
- 各 issue は、それ単体で検証やデモができる粒度を目指す。
- 機能・成果単位を基本にする。実装手順を細切れにせず、担当・依存・検証・再開の単位が分かれる場合だけ子Issueへ分ける。
- ブロッカーを曖昧にしない。
- PRD の内容を丸写しせず、その issue で作る end-to-end の価値を書く。

## 各 issue に含めるもの

```md
## 親PRD

PRDのパスまたはURL

## 作るもの

この縦切りで実現する end-to-end の振る舞い。

## 受け入れ条件

- [ ] 条件1
- [ ] 条件2
- [ ] 条件3

## Blocked by

- LinearのIssue IDとURL

依存がなければ "なし"

## 対応するユーザーストーリー

- User story 3
- User story 7
```

## 確認観点

- 粒度は粗すぎないか
- 依存関係は正しいか
- 分割より統合すべき issue はないか
- 最初に着手すべき tracer bullet が明確か

## 完了条件

- 全 issue が薄い縦切りになっている
- 依存関係が明示されている
- 各 issue に受け入れ条件がある
- PRD のどのユーザーストーリーに対応するか追える

実際に別の実行者へ引き継ぐ時は `plan-handoff` で実行指示書にする。同じ環境で実装を続ける場合は必須にしない。要件ID/Test IDと検証記録は `templates/linear-issue.md` に合わせる。
