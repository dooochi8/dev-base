# TDD

期待される振る舞いをテストで表現できるときに使う。特にバグ修正や、振る舞いが中心の機能追加で有効。

## 基本ループ

1. 観測可能な振る舞いを一つだけ表すテストを書く。
2. 実行して失敗を確認する。
3. そのテストを通す最小限のコードを書く。
4. 再実行して成功を確認する。
5. 緑に戻ってからだけリファクタする。

## 良いテストの条件

良いテスト:

- 公開インターフェースか安定した境界から振る舞いを確認する
- 内部リファクタで壊れにくい
- 小さな仕様として読める

悪いテスト:

- 内部の呼び出し構造を検証する
- 自分で管理していない協調先を過剰にモックする
- 振る舞いが同じなのに実装変更で壊れる

## アンチパターン

次のように一括で進めない。

- テストを大量に書く
- 実装をまとめて書く
- 最後にまとめて整える

これは横切りであり、学習が遅く、テストも弱くなりやすい。

## 実務上のデフォルト

- 最小の失敗する振る舞いから始める。
- バグは可能なら失敗テストで再現する。
- 各サイクルは短く保つ。
- テストが書きづらいなら、まずインターフェース設計を疑う。
