# mistake-to-rule

エージェントのミスを、次のエージェントが読み飛ばせない仕組みに変える。文章の注意書きは強制できないため、最後の手段にする。考え方は `principle-encode-lessons-in-structure`、層の順序と `harness-check` の使い方は `docs/harness.md` を正本とする。

## ガードレール

- 依頼の範囲で許されていなければ、ルールを追加・有効化せず、提案として示す。ルールは以後のすべてのエージェントの作業を変えるため、人間が採否を決める。
- 新しいルールを通すために、既存ルールの `pattern` を緩めたり、`allow` を広げたり、既存違反を baseline へ足したりしない。
- 症状を隠す方法を `message` に書かない。根本原因の直し方を書く。
- 一回限りの判断ミスを、無理に正規表現にしない。

## 進め方

1. **ミスを取り出す。** 1文で何が誤りかを書き、最小の悪例（そのまま書かれた1行）と、正しく直した1行を取り出す。人間の修正差分やレビュー指摘があれば、そこから引用する。
2. **繰り返すかを確かめる。** 同じ指摘が2回目か、コードベースの他の場所にも同じ形があるかを検索する。一回限りなら、その場で直して終える。
3. **最も強い仕組みを選ぶ。** 上から順に検討し、使える最初のものを選ぶ。選ばなかった上位の仕組みは、使えない理由を一言残す。
   1. 表現できない形にする: 型、API設計、ディレクトリ構造で、誤った書き方をコンパイルできなくする。
   2. コンパイラ・型チェックの設定を強める。
   3. AST ベースの lint ルール（既存 lint のルールを有効化する、またはカスタムルールを書く）。
   4. `harness-check` のルール: 1行の正規表現で検出でき、許可する場所を `allow` で表せる場合。
   5. 正規の補助関数を用意し、危険な API を 3 か 4 で禁止する。
   6. 実行時の検査、または振る舞いのテスト。
   7. 文章（AGENTS.md・スキル）: 判断が必要で機械化できない場合だけ。失敗例を添えて短く書く。
4. **ルールを書く。** `harness-check` の場合は、次の形で `harness.config.json` に追加する。

   ```json
   {
     "id": "<短い英語のID>",
     "pattern": "<1行に当てる正規表現>",
     "include": ["<対象を絞る場合>"],
     "allow": ["<正規の抽象を置く場所>"],
     "message": "<根本原因の直し方と、正しい置き場所>",
     "examples": { "bad": ["<手順1の悪例>"], "good": ["<手順1の正しい例>"] }
   }
   ```

5. **失敗できることを証明する。** 次をこの順に実行し、出力を残す。
   - `node scripts/harness-check.mjs --self-test`: 悪例で失敗し、良例を通すことを確かめる。通らなければ `pattern` を直す。悪例・良例を削って通さない。
   - 実際のミスを一時的に再現した状態で `node scripts/harness-check.mjs` を実行し、新しいルールの `message` 付きで失敗することを確かめる。再現は戻す。
   - lint・型・テストを選んだ場合も同じく、ミスを再現して失敗すること、直した形で通ることを確かめる。
6. **既存の違反を扱う。** 新しいルールが既存のコードに当たる場合は、同じ変更で直すことを優先する。量が多く別の変更に分けるなら、人間がルールの追加を承認した後に `node scripts/harness-check.mjs --adopt <id>` で、そのルールの既存違反を一度だけ記録する。違反がなくても `--adopt` で採用済みにし、後から上限を足せないようにする。PR に記録した件数を書き、人間のレビューを受ける。既存ルールの上限は増やさない（採用済みのルールへの `--adopt` は拒否される）。
7. **文章を消す。** 同じ内容の注意書きが AGENTS.md やスキルにあれば削除する。仕組みと文章を二重に持たない。

## 報告

```markdown
## ミス
<1文>。悪例: `<行>` / 正しい例: `<行>`

## 選んだ仕組みと理由
<仕組み>。上位の仕組みを使わない理由: <一言ずつ>

## 変更
<ファイルと追加したルール。提案だけの場合は「未適用（提案）」>

## 証拠
- `--self-test`: <出力>
- ミスを再現した検査: <失敗した出力の要点>
- 直した状態の検査: <出力>

## 既存違反と残り
<直した件数、baselineへ写した件数と理由、削除した注意書き>
```

## 完了条件

- 選んだ仕組みが、実際のミスで失敗し、正しい形で通ることを実行で示した。
- `harness-check` のルールには `examples.bad` と `examples.good` があり、`--self-test` が通る。
- 新しいルールは `--adopt` で採用済みになり、既存ルールの baseline の上限を増やしていない。
