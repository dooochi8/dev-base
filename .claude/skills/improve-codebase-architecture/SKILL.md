# Improve Codebase Architecture

コードベースを探索し、設計上の摩擦を見つけ、改善候補を整理する。

## 目的

- AI でも人でも追いづらい箇所を見つける
- テストしづらい構造の原因を特定する
- 浅いモジュールの連鎖を、より深い境界へ寄せる
- リファクタ候補を、実行可能な単位で言語化する

## 進め方

1. コードベースを実際に探索し、理解しづらい箇所や変更しづらい箇所を探す。
2. 摩擦の強い候補を複数挙げる。
3. 各候補について、どの概念が分散しているか、なぜ結合が強いかを説明する。
4. どこに単純な境界を作れそうかを考える。
5. 必要なら複数のインターフェース案を比較する。
6. 最終的に、どの改善から手をつけるべきかを提案する。

## 見るべき摩擦

- 一つの振る舞いを追うのに、多数の小さなファイルを往復する
- 変更のたびに複数モジュールを同時に触る必要がある
- ヘルパーは多いのに、責務の中心が見えない
- テストしやすくするための分割が、逆に統合リスクを増やしている
- 公開インターフェースが実装と同じくらい複雑

## 出力形式

各改善候補について、少なくとも次を示す。

- 対象の責務やモジュール群
- なぜ今は扱いづらいのか
- どの複雑さを内側へ隠したいのか
- どんな境界を作ると改善しそうか
- テストへの影響
- 着手優先度

## 原則

- 細かい美しさより、変更容易性と理解容易性を優先する。
- ヘルパー抽出を増やすだけで満足しない。
- deep module を目指すが、抽象層を増やすこと自体を目的にしない。
- 振る舞いを変えないリファクタと、仕様変更を混ぜない。

## 完了条件

- 主要な設計摩擦が列挙されている
- 改善候補ごとに理由と方向性がある
- どこから着手すべきかの優先順位がある
- 必要なら次の issue や計画に落とせる粒度になっている
