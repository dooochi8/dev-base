# TDD

red-green-refactor を短く回しながら、振る舞いを中心に機能追加やバグ修正を進める。

## 基本姿勢

- テストは振る舞いを確認するために書く。
- 実装詳細ではなく、公開インターフェースや安定した境界から検証する。
- 一度に一つのテストだけ進める。
- 緑に戻る前にリファクタしない。

## 進め方

1. まず何を確認すべき振る舞いかを明確にする。
2. その振る舞いを表すテストを一つだけ書く。
3. 失敗を確認する。
4. そのテストを通す最小限の実装を書く。
5. 成功を確認する。
6. 必要なら小さくリファクタする。
7. 次の振る舞いに進む。

## 良いテスト

- ユーザーや呼び出し元から見える振る舞いを確認する
- 内部構造が変わっても壊れにくい
- 何を保証しているかを自然に読める

## 悪いテスト

- private な実装詳細に依存する
- 内部の呼び出し回数や順番ばかり検証する
- モックしすぎて本当の振る舞いが見えない
- 実装変更だけで壊れる

## アンチパターン

- テストを先に大量に書く
- 実装をまとめて後から追いつかせる
- テストが通っていない状態で設計整理を始める

これらは red-green-refactor ではなく、学習も修正も遅くなる。

## 実務上の判断

- バグ修正なら、まず失敗ケースの再現を狙う。
- 新機能なら、最初の tracer bullet になる最小テストから始める。
- テストが書きづらいなら、インターフェースや責務分割が悪い可能性を疑う。
- 複雑さが増えたら、deep module に寄せて境界を整理する。

## 完了条件

- 重要な振る舞いがテストで表現されている
- 各テストが短い red-green のサイクルで追加されている
- 緑の状態で終わっている
- 必要なら最小限のリファクタが済んでいる
