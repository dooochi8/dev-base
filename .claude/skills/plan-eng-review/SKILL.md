# Plan Eng Review

要件定義段階のプロダクトをエンジニアリング視点でレビューする。実装前に複雑化・抜け漏れ・危険な前提を見つける。

## 対象と境界

- 対象リポジトリの要件、仕様、MVP、実装計画、技術選定メモ、データ設計、API設計、運用メモ、ユーザーが貼った機能仕様を扱う。
- 依頼と既存資料から対象を決める。候補が複数あり結果を変える場合だけ質問し、スキルの導入先や個人環境の保存先に固定しない。
- 既存の設計・制約・受入条件を読み、必要な範囲でコードやテストを読み取り確認する。資料に書かれた事実と推測、未確認を分け、指摘には根拠箇所と影響を添える。
- レビュー依頼だけでコード実装、仕様ファイルの変更、依存追加、外部への更新を始めない。修正案を提示し、保存・反映は依頼された範囲で行う。
- スキルの導入・コピー依頼は、レビュー実行の指示ではない。

## 見る観点

- 要件が実装単位に分解できるか
- データモデル、状態、権限、外部連携の前提が書かれているか
- MVPに不要な技術的野心が混ざっていないか
- エラー、空状態、重複、再試行、同期ズレなどの扱いがあるか
- 初回リリースに必要な非機能要件が明確か
- 実装順序がリスクの高い順になっているか
- 手動運用でよい箇所を自動化しすぎていないか

## 出力

```markdown
## 技術判定
Ready / Needs narrowing / Risky / Under-specified のいずれかと、その理由

## Eng視点の指摘
- [P1] 根拠箇所 / 問題と影響 / 改善案
- [P2] 根拠箇所 / 問題と影響 / 改善案

## 足りない仕様
- 実装前に確定すべき条件

## スコープ削減案
- 初回に必要な価値を保ちながら削れること

## 推奨実装順
1. 高いリスクを早く確かめる最初の成果
2. 依存関係に沿う次の成果

## 未確認事項
- 読み取れなかった資料や、検証が必要な仮説
```

P1は実装前に解消すべき問題、P2は明示した条件下で対応すべき問題とする。指摘がない時に架空の問題を作らず、確認した観点を示す。

## 原則と完了条件

- 新しい技術より、失敗しにくい単純な構成を優先する。
- 「あとで必要そう」ではなく「初回ユーザーが使うために必要」で判断する。
- Readyは計画を進められる判定であり、コードの動作・性能・安全性を検証済みという意味ではない。
- 対象、判定根拠、足りない仕様、推奨順、未確認が読み手に分かる状態で終える。コード実装には進まない。
- 画面と導線の計画は `plan-design-review`、実装差分のバグ確認は `review-diff` と役割を分ける。全スキルを毎回起動しない。
