# Plan Handoff

計画者（高性能モデルや人間）が実行者（軽量モデル）に渡す実行指示書を作る。
実行者が指示書だけを見て、質問なしで着手・完了判定できる状態にすることが目的。

## 原則

- 実行者は指示書だけを見て作業する前提で書く。
- 曖昧語（「適切に」「いい感じに」「必要に応じて」）を使わない。
  - 悪い例: 「適切なエラー処理を追加する」
  - 良い例: 「`fetch` が 4xx/5xx を返したとき `ApiError` をスローする」
- 検証コマンドは実際に手元で実行し、存在を確認したものだけ書く。
- 受け入れ条件は観測可能な振る舞いで書く。主観的な判断を要求しない。

## ガードレール

- コードベースを確認せずに「触るファイル」や「検証コマンド」を書かない。
- 作業の粒度が大きすぎる場合は、tracer bullet を最初のスライスとして切り出す。
- 禁止事項は明示する。書かれていないことは実行者が判断しなければならなくなる。
- 指示書の長さが膨らむなら、作業スコープを削るほうを優先する。

## 進め方

1. 依頼を受けたら、まずコードベースを探索して現状の実装・制約・テスト実行方法を確認する。
2. この作業で実現する**観測可能な振る舞い**を一文で言い直す。
3. 変更が想定されるファイルと、それぞれで何をするかを列挙する。
4. 最初に通す tracer bullet（最小の縦切り）と、続くスライスの順番を決める。
5. 受け入れ条件を観測可能な形で書く。
6. 検証コマンドを実際に実行して動作を確認したうえで記載する。
7. 触らないもの・禁止事項を明示する。
8. 以下のテンプレートに沿って指示書をまとめる。

## 実行指示書テンプレート

```md
## 目的
この作業で実現する観測可能な振る舞い。

## 触るファイル
変更が想定されるファイルと、それぞれで何をするか。

## 触らないもの・禁止事項
- リファクタしてはいけない箇所
- 追加してはいけない依存・抽象
- スコープ外の変更

## 手順（縦切り）
1. 最初に通す tracer bullet
2. 以降のスライス

## 受け入れ条件
- [ ] 条件（観測可能な形で）

## 検証コマンド
実行者が完了前に必ず実行するコマンド。

## 報告フォーマット
変えたもの / 実行した検証と出力 / 未確定・未検証のこと
```

## 完了条件

- 実行者が質問なしで着手できる
- 受け入れ条件が観測可能で、機械的に判定できる
- 検証コマンドの実在が確認されている
- 触らないものと禁止事項が明示されている
