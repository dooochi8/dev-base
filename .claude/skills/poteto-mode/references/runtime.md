# dev-baseでのpstack実行対応

このリポジトリはpstack-claudeのskills-only移植。日本語の入口とこの対応表を適用してから、各スキルの `UPSTREAM-SKILL.md` を読む。原文のplaybook・参照・スクリプトは同じスキルフォルダに保持する。この対応表は移植による差分であり、ユーザー・実行環境の上位指示を変更しない。

## 手順と参照

- 通常の開発は `poteto-mode` が依頼に対応するplaybookを選ぶ。必要な工程をタスクリストへ写し、対象外の工程には理由を残す。相談・調査は読み取りのまま終える。
- `Skill`、`/pstack:<name>`、`/name` はトップレベル `<name>/SKILL.md` を読む意味。原文へ直接飛ばず、日本語の入口を経由する。原文中の相対パスは、その原文ファイルのあるフォルダを基準に解決する。
- `UPSTREAM-SKILL.md` は元のSKILL.mdと同じ階層に置いている。`<plugin>/skills/<name>/...` は、このリポジトリの `<name>/...` に読み替える。`plugins/pstack/models.json` は出典の既定値であり、この環境の設定元ではない。
- タスクリストは利用できる計画・タスクツールを使う。なければ既存のIssue/作業メモ、またはGit管理外のローカルチェックリストへ記録する。目標管理ツールの起動を通常の依頼から推定しない。
- 返答、作業メモ、PR、変更したスキルの本文は日本語。上流原文、コードの識別子、ログの引用は原文を保持する。説明用の英語見出しは日本語に置き換えてよい。check-plan等が照合する機械向けの項目名・テンプレートは原文のまま保持する。

## 実行環境

利用できるツール名・引数は、そのセッションの定義で確認する。原文の名前と一致することを仮定しない。

| 原文の操作 | Codex | Claude Code |
|---|---|---|
| Read / shell / 検索 | ファイル読取・実行ツール。検索はrgから | Read / Bash / Grep等 |
| ファイルの作成・編集 | apply_patch等のファイルツール | Edit / Write等 |
| Skill | このリポジトリの日本語SKILL.mdを読む | 同期されたローカルスキルを呼ぶ |
| Agent / Task | 利用可能で許可されたspawn_agent | 利用可能で許可されたAgent |
| 待機・停止 | 実際に公開されている待機・停止ツール | 実際に公開されている待機・停止ツール |
| AskUserQuestion | 利用可能な質問ツール、または対話 | AskUserQuestion、または対話 |
| ブラウザ・アプリのdriver | 利用可能なブラウザ・アプリ操作ツール | 利用可能なブラウザ・アプリ操作ツール |

CodexのCode Modeでは、同じ段階の独立したfunctions.exec内ツールを `Promise.allSettled` 等でまとめて実行し、全結果を確認する。依存する操作、待機、書込、結果次第で変わる調査は順に行う。collaborationツールはfunctions.execの外で呼ぶ。

`run` やdriverという名前のスキルがない場合も、対象アプリ・CLI・サービスを実際に動かす工程は残す。操作できない対象は、到達できた範囲と残る具体的な確認を報告する。コード読取・ビルド成功・他担当の報告だけで動作確認を代替しない。

## 担当とモデル

- pstackの調査・設計・実装・レビューの担当分離を基本にする。サブエージェントは上位指示が許可し、機能が利用可能な場合に使う。許可されない環境では同じ工程を順に行い、独立レビュー・複数モデル比較を未実施として報告する。
- このskills-only配置では `pstack:poteto-agent`、`pstack:effort-*`、Comment Sickoの専用エージェントは登録していない。利用可能な通常エージェントへ、`poteto-mode/SKILL.md` と担当スキル、所有範囲、成果、検証、禁止事項を渡す。専用タイプの登録やプラグイン導入を成功したことにしない。
- `interrogate` は読み取りレビュー。指摘を根拠と照合して採否を決める。レビュー依頼だけで修正を始めない。実装タスクの中では採用した指摘に起因する修正と再検証まで進める。
- 書込担当には専用worktree・出力先を与える。同じファイルの編集、同じcheckoutでの編集と検査を競合させない。読み取り担当にも子担当の禁止事項と参照可能な範囲を引き継ぐ。
- `opus` / `fable` / `sonnet` や上流のGPT名を固定して起動しない。指定がない担当はセッションのモデル・推論量を継承する。ユーザーが指定したモデルや推論量を優先し、その環境での利用可否と対応する引数を確認する。固定モデルのエージェント役割を選ぶ場合は、その制約を把握して報告する。
- 複数モデルのパネルが指定・利用可能なら異なるモデルを使う。同一モデルの独立した実行は独立レビューとして報告し、複数モデルレビューとは呼ばない。代替モデルが必要でも、ユーザーの指定を黙って置き換えない。

## プロジェクト設定

`setup-pstack` はこの対応表の設定方法を使う。依頼されたモデル設定だけを、Git管理外のプロジェクトルート `.pstack-models.md` へ書く。存在する場合は現在値を読んで必要な行だけ更新し、同じファイルを読み戻す。`poteto-mode` と各担当は、実行するリポジトリルートにこのファイルが存在する場合だけ読む。

書式は上流のrole行に合わせる。例は `feature, refactoring: inherit-parent`、`interrogate reviewers: inherit-parent, inherit-parent`、`default effort: session`。後者は同一モデルの独立レビューであり、モデルの多様性はない。実モデルを指定する場合は、そのセッションで検証した識別子を使う。

本移植にはSessionStart hook・plugin manifest・Codex slash stub・Claude専用agent・Pi拡張を含めない。hook行は適用されない。標準入口はAGENTS.mdから選ぶ。setupの実行を理由に、グローバル設定・hook・MCP・承認・モデルへのアクセスを変更しない。既存の `.codex/config.toml` はプロジェクト起動の既定値で、現在のチャットの選択を変更するものではない。

## 既存運用との接続

- 開発の目的・状態・完了条件は `linear-workflow` と `./scripts/linear`、仕様と設計判断はdocs、差分とレビューはGit/GitHub。GitHub Issuesへ二重起票しない。原文の「tracked issue」はこのLinear運用へ読み替える。
- 原文のOpening a PRは、コード・スキル等を変更して成果を提示する時に使う。読み取りの調査・説明・レビューだけでは起票・コミット・PR作成を行わない。既存の未コミット変更を消したり、自分の変更と混ぜてコミットしたりしない。原文のreset・強制push・自動マージ例を許可と解釈しない。
- 実装に必要なら `search-first`、認証・認可・外部入力・秘密情報・決済の境界には `security-review`。要件が未確定なら `grill-me` / `grilling` / `write-a-prd`、必要な実装前レビューには `plan-eng-review` / `plan-design-review` を使う。
- 完了ゲートは既存の `verify`。pstackの実行面に合った検証と併用し、失敗・未実施・対象外を区別する。`create-verification-skill` はトップレベルの `verify/` のプロジェクト固有参照へ追加する。入口・既存の必須検査を消さず、`.agents/skills` や `.claude/skills` を直接編集しない。
- UIの実装と仕上げにはEmilスキル群。`prototype` 等の明示呼び出し条件は、移植を理由に解除しない。pstackの試作工程で必要なら利用可能な通常の実装方法で比較する。
- スキルの作成・改訂はプラットフォームのskill-creator等を使う。トップレベル正本を編集して同期し、両入口を検査する。`reflect` の提案も同じ入口でレビューし、無関係な個人メモリや他プロジェクトを書き換えない。
- `recall` / `reflect` / session pickupは現在の会話、対象Issue・ブランチ、利用が許可された対象チャットを使う。CodexでClaudeの全履歴を探索しない。取得できない履歴は作業要約で代替し、その限界を記録する。

## 長い実行と補助スクリプト

原文の23 playbookと補助スクリプトは保持する。通常のタスクに全工程を当てはめず、選択したplaybookだけを読む。独立した比較案・レビュー・各工程の検証証拠を残す。

継続監視や後日の再開を依頼された場合は、その環境のautomation等を使う。原文の `/loop` を、終了後も続く実行機能と扱わない。既存のIssue・実装メモに再開可能な状態を記録する。

補助スクリプトは使用前に対象と依存を確認する。Node.jsで動く検査と、bun・gh・gt等が必要なPR監視やorchestratorを分ける。依存をインストールしていない状態を「利用可能」としない。通常の開発のために全依存を一括導入しない。認証、外部書込、顧客連絡、マージ、デプロイの許可はユーザーの依頼と上位指示に従う。
