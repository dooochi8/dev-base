# review-diff

差分を完了前にレビューする。「動くか」ではなく「どんな条件で壊れるか」を探す。

## 基本姿勢

- 「動くか」ではなく「どんな条件で壊れるか」を探す。
- 指摘は根拠とセットで書く。「気になる」は指摘ではない。
- スコープ外の設計改善は指摘リストに混ぜず、別枠に分ける。

## ガードレール

- スコープ外の設計改善を指摘リストに混ぜない。`improve-codebase-architecture` 行きとして別枠に書く。
- 指摘ゼロのときは「確認した観点」を列挙する。何も確認しなかった結果ではないことを示す。
- コードスタイルの好みを high 指摘にしない。

## レビュー観点

### 正しさ
- エッジケース: 空リスト、null/undefined、ゼロ除算、文字列境界など。
- エラー処理: 例外が握りつぶされていないか。失敗時の振る舞いが定義されているか。
- 境界値: 数値・インデックス・日時の境界で正しく動くか。
- 並行性: 競合状態、共有状態への非同期アクセス、冪等性。

### 要件との一致
- 受け入れ条件を本当に満たしているか。
- 変更が意図した振る舞いを変えていないか（意図しないリグレッション）。

### 単純化
- 不要な抽象・インターフェース・レイヤーが増えていないか。
- dead code が混入していないか。
- 既存ユーティリティの再発明をしていないか。

### テスト
- 振る舞いを検証しているか（実装詳細ではなく）。
- 追加した振る舞いにテストが対応しているか。
- モックしすぎて本当の振る舞いが見えなくなっていないか。

## 出力フォーマット

```
## 指摘

| 重要度 | 場所 | 何が問題か | 提案 |
|--------|------|-----------|------|
| high   | ...  | ...       | ...  |
| medium | ...  | ...       | ...  |
| low    | ...  | ...       | ...  |

## スコープ外（improve-codebase-architecture 行き）
- <設計改善の観点があれば列挙。なければ「なし」>

## 確認した観点
- <指摘ゼロの場合、確認した観点を列挙する>
```

重要度の基準:
- **high**: バグ・データ破壊・セキュリティ問題など、マージ前に必ず直すべきもの。
- **medium**: 動作に影響する可能性があるが、条件が限定的なもの。
- **low**: 読みやすさ・保守性の観点での改善提案。

## 完了条件

- 4つの観点（正しさ・要件との一致・単純化・テスト）を全て確認した。
- 指摘はフォーマットに従って記載されている。
- 指摘ゼロの場合は「確認した観点」が列挙されている。
- スコープ外の設計改善は別枠に分けて記載されている。
