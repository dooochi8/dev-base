# Smart Docs

実際のコードを根拠に、後から読み返せる日本語の開発資料を作る。構成の概要から依存関係・主要な処理・必要な詳細へ段階的に掘り下げ、MarkdownとMermaidで保存する。

## 入力と境界

- 対象リポジトリ、対象範囲、作成・更新する資料を依頼と既存文書から決める。対象が複数候補に分かれる時だけ質問する。スキルのインストール先や親フォルダを解析対象と決めつけない。
- ユーザー指定と対象リポジトリの規約・命名・既存文書を優先する。指定も既存の置き場もなければ対象リポジトリの `docs/` を使う。既存文書は該当箇所だけ更新し、人の注記や未確認事項を勝手に消さない。
- コードから確認した事実、既存文書に書かれた設計意図、推測を区別し、根拠ファイルを示す。未実行のコマンドを動作確認済みにせず、根拠のない解析率・精度・所要時間を作らない。
- `.env`、秘密鍵、トークン、個人情報・実データを含むファイルを展開・転載しない。設定項目は公開されたサンプルや変数名を根拠に説明する。コードを外部サービスへ送らない。
- 文書化の依頼で、アプリの実装変更・依存追加・リファクタ・デプロイ・Gitの公開操作まで行わない。改善候補は提案として分ける。
- 追加のLLM APIやdeepwiki-rs本体は不要。現在の対話エージェントで実行し、利用中サービスの通常の料金・利用枠が適用される。
- ツール名は実行環境に読み替える。ファイル編集・権限などは環境の規則に従う。補助ツールがなくても調査は続け、検証できない部分を明示する。

## 他スキルとの使い分け

- `orient`: 入口や主要経路を素早く把握する。保存する詳細資料が不要ならこれで十分。
- `show-me`: 一つの関係・処理・設計案を図解して説明する。
- `smart-docs`: コードに基づく構成・処理・開発ガイドを資料として作成・更新する。
- スキルの追加・コピー依頼は文書生成の実行依頼ではない。導入だけでリポジトリ全体を解析しない。

## 進め方

### 1. 入口と既存資料を確認する

README、開発ガイド、公開された設定例、依存定義、エントリポイント、テストの配置を調べる。検索は `rg --files` / `rg` を優先し、依存・ビルド成果物・生成物・Git内部は除く。

言語・フレームワーク・実行方法を実ファイルから特定する。ファイル数や行数が調査計画に必要な時だけ数える。読み取れない箇所は未確認として残す。

### 2. 構造と主要経路を調べる

入口から代表的なユーザー操作や処理を追い、次を必要な範囲で整理する。

- モジュールの責務、内部依存、外部サービスとの接点
- データモデル、状態の持ち方、権限の境界
- API・公開インターフェース、正常系のデータの流れ
- エラー、再試行、空状態など、実装やテストで確認できる分岐
- テストの対象・実行方法と、調査で確認していない部分

大きなリポジトリでは主要な機能から順に扱い、概要を保存してから指定モジュールの詳細へ進む。全ファイルを読み切ることや全モジュールの資料作成を必須にしない。

言語ごとの確認対象の例:

- Rust: crate / module、trait、非同期処理、所有権やエラーの境界
- Python: package、入口、APIルート、依存・実行環境
- Java: package、ビルド定義、サービス層とフレームワーク設定
- JavaScript / TypeScript: UI構成、状態管理、ルート、ビルド設定、型の境界
- その他の言語でも、依存定義と入口から同じ観点で追う。

### 3. 必要な資料だけ作成・更新する

文書を書き始める前に [構成例](references/documentation-templates.md) を読む。既存の形式があればそちらを優先し、例の全ファイル・全見出しを埋めるためだけに資料を増やさない。

1. 概要: 目的、主な機能、技術構成、ディレクトリ、開発の始め方。
2. 設計: システム境界、実行単位、コンポーネント、依存関係。設計判断は出典を示し、不明なら意図を推測で断定しない。
3. 処理フロー: 主要操作、データの流れ、状態遷移、エラー処理。
4. 詳細: 必要なモジュールの責務、主要ファイル、インターフェース、テスト。

関連文書は相対リンクで結ぶ。資料内のコードへのリンクは文書の位置を基準にし、複製先で壊れる個人環境の絶対パスを書かない。

### 4. 図を作り、検証する

構造はC4のシステム境界・実行単位・コンポーネントの粒度で整理する。描画環境がC4構文に対応しなければ、同じ粒度をMermaidのflowchart等で表す。処理順はsequenceDiagram、状態はstateDiagram、データ関係はerDiagramなど、説明する関係に合うものを選ぶ。

図は一つの論点に絞り、10〜12ノードを超えて読みづらくなるなら分ける。凡例や矢印の意味を明確にし、存在しない構成を足さない。短文や表で十分な箇所には図を強制しない。

保存後に資料と参照リンクを再読取する。コード例・ファイル名・依存の方向を照合し、未置換の見本を残さない。利用可能な検証・プレビューで図を確認し、「構文確認」と「実際の描画確認」を分けて報告する。描画環境がなければ未確認と書き、自動で依存を追加しない。

## 完了条件と報告

- 依頼された範囲の資料が保存され、生成・更新したファイルと参照リンクを確認している。
- コード上の事実、設計意図の出典、推測・未確認が区別されている。
- 既存文書の対象外部分とアプリのコードを保持している。
- 生成したファイルへのリンク、調査範囲、実施した検証、未確認事項を簡潔に伝える。未検証の実行結果・図の描画・網羅性を完了扱いしない。
