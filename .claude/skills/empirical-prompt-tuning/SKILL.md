# empirical-prompt-tuning

書いた本人の自己評価を信じない。別実行者に実際に読ませ、詰まり方を観察して直す。

このスキルの導入・コピーだけを依頼された場合は評価を起動しない。評価対象・シナリオ・利用できる実行環境を確認し、実行評価を行った範囲だけ報告する。外部書込が必要なシナリオは隔離したfixtureで評価し、実アカウント操作の許可を評価依頼から推定しない。

## 使う場面

- 新しい skill を作った直後
- AGENTS.md や長いワークフロー指示を大きく変えた直後
- エージェントの挙動が不安定で、原因が指示文にありそうな時
- 再利用頻度が高いプロンプトを堅牢化したい時

使わない場面:

- 一回限りの使い捨てプロンプト
- 好みの文体調整だけをしたい時
- 実行者を分けずに雰囲気で直したいだけの時

## ワークフロー

### 0. 静的整合チェック

対象テキストだけを読み、次を確認する。

- description が謳う用途と body が一致しているか
- 出力形式が本文で定義されているか
- 禁止事項と許可事項の境界が曖昧でないか

大きなズレがあれば、実行評価の前に直す。

### 1. ベースライン準備

対象ごとに次を固定する。要件は後から動かさない。

- 評価シナリオ 2-3 本
- 要件チェックリスト 3-7 項目
- 各チェックリストに `[critical]` を 1 項目以上

### 2. 評価方式を選ぶ

| 条件 | モード |
|---|---|
| 独立実行の機能が使え、上位指示で許可されている | A. subagent 評価（デフォルト） |
| 機能または権限がない | B. 構造審査モード + 報告に「実行評価は未実施」を必ず明記 |

### 3. dispatch

自己再読で代替しない。評価シナリオごとに新規 subagent を使い、同一 subagent を使い回さない。

実行者に渡す依頼は次の構造を守る。対象プロンプトが 150 行以下なら全文を貼る。151 行以上ならパスを指定して Read させる。

```text
あなたは <対象名> を白紙で読む実行者です。

## 対象プロンプト
<150 行以下なら全文。151 行以上なら Read 対象パス>

## シナリオ
<使用場面>

## 要件チェックリスト
1. [critical] ...
2. ...
3. ...

## タスク
対象プロンプトに従ってシナリオを実行し、最後にレポートを返す。

## レポート構造
- 成果物
- 不明瞭点
- 裁量補完
- 再試行回数
```

実行者に ○ / × / 部分的 を自己判定させない。自己採点は甘くなり、軽量モデルほど判定がブレる。

### 4. 評価者側で判定する

呼び出し側が成果物を要件チェックリストと突き合わせ、○ / 部分的 / × を決める。

| 軸 | 取り方 |
|---|---|
| 成功/失敗 | `[critical]` 項目が全て ○ なら成功 |
| 精度 | ○=1、部分的=0.5、×=0 |
| steps | 実行者のツール呼び出し量 |
| duration | 実行時間 |
| retries | 実行者の自己申告 |
| 不明瞭点 | 自己申告から抽出 |
| 裁量補完 | 自己申告から抽出 |

steps が他シナリオ比で 3 倍以上なら、自己完結性が低いサインとして扱う。精度 100% でも、不明瞭点や steps 偏りがあれば続行候補にする。

### 5. 集計スクリプトを実行する

次の JSON を作り、スキル内スクリプトで集計する。精度計算と収束判定は手計算しない。

各要件の `text` にチェックリストの固定文言を必ず入れる。空欄・同一シナリオ内の重複は禁止。反復間で文言・順序・critical指定を変えない。要件を変更する場合は、別のベースラインとして評価をやり直す。

```json
{"iterations":[{"scenarios":[{"name":"A","requirements":[{"text":"未実施を成功にしない","critical":true,"result":"ok"},{"text":"変更内容を説明する","critical":false,"result":"partial"},{"text":"草案を保存する","critical":false,"result":"ok"}],"tool_uses":4,"duration_ms":20000,"retries":0,"new_unclear":2},{"name":"B","requirements":[{"text":"失敗を成功にしない","critical":true,"result":"ok"},{"text":"未解決事項を示す","critical":false,"result":"ok"},{"text":"外部に投稿しない","critical":false,"result":"ok"}],"tool_uses":3,"duration_ms":15000,"retries":0,"new_unclear":0}]}]}
```

```sh
python3 <このSKILL.mdがあるフォルダ>/scripts/ept_score.py ept-input.json
```

CodexとClaudeのどちらから読んでも、実際に読んだSKILL.mdのフォルダを基準にパスを解決する。スクリプトを実行できない場合だけ `references/manual-scoring.md` を読む。入力不備や実行エラーを手計算で成功扱いしない。

### 6. 差分適用と再評価

- 不明瞭点を潰す最小修正を入れる
- 1 イテレーションで直すテーマは 1 つに絞る
- 新しい subagent で再度評価する
- 3 回回しても新規不明瞭点が減らないなら、差分修正をやめて構造を書き直す

### 7. 収束判定

停止条件はスクリプト出力の「収束判定」を使う。

- 新規不明瞭点 0 件
- 精度が悪化せず、改善が +3pt 以下
- steps 変動が ±10% 以内
- duration 変動が ±15% 以内
- 連続クリア回数 2/2

前提として各回2本以上の同じシナリオ・同じ固定要件を評価し、すべてのcritical要件を満たすこと。失敗が安定しているだけの結果を収束にしない。

重要な skill は最後に、通常評価では使っていない hold-out シナリオ 1 本を確認する。`iterations` 内には追加せず、同じJSONのトップレベルへ `holdout` として指定する。通常シナリオと同じ必須フィールドを持たせ、別の名前にする。具体例は `references/example-run.md` を参照。

スクリプトは通常評価だけで収束を計算し、hold-out 精度を最終iterationの通常シナリオ平均と比較する。15ポイント以上の低下は過適合、critical未達も不合格。hold-outを指定した場合の総合判定は、通常評価の収束とhold-out合格の両方を必要とする。未指定時は「未実施」と表示するため、重要なskillでは総合判定だけを見て完了にしない。

## 提示フォーマット

```markdown
## Iteration N

### 変更点
- ...

### 結果
| シナリオ | 成功/失敗 | 精度 | steps | duration | retries |
|---|---|---|---|---|---|
| A | ○ | 90% | 4 | 20s | 0 |

### 不明瞭点
- ...

### 裁量補完
- ...

### 収束判定
| 条件 | 判定 |
|---|---|
| 新規不明瞭点0件 | ○/× |
| critical要件を全件達成 | ○/× |
| 精度悪化なし・改善+3pt以下 | ○/× |
| steps±10% | ○/× |
| duration±15% | ○/× |
| 連続クリア回数 | N/2 |

### 次の修正案
- ...
```

## 具体例

- 入力形式や記録例が必要な時は `references/example-run.md` を読む。

## やらないこと

- 自己再読だけで empirical 評価したことにしない
- シナリオを 1 本だけにしない
- 1 回で大量修正しない
- 結果が良いから質的フィードバックを無視しない
- 同一 subagent を使い回さない
- 実行者の自己採点を評価結果として使わない
