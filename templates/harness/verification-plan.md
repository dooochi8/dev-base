# 検証計画

このプロジェクトでエージェントの変更を証明する手段の一覧。[ハーネス設計](harness.md) の段階2を、このプロジェクトでどこまで導入したかを記録する。各行の状態は「未着手」「導入済み」「対象外（理由）」のいずれかにする。導入済みにする時は、実行したコマンドと結果を根拠として残す。

## 段階1：決定論的な検査

| 手段 | 状態 | 実行コマンド | 根拠 |
|---|---|---|---|
| harness-check | 導入済み | `node scripts/harness-check.mjs` | 複製時に違反0件・全ルール採用済みの `harness-baseline.json` を作成。ルールを足したら `--adopt <rule>` |
| ルールの自己検査 | 導入済み | `node scripts/harness-check.mjs --self-test` | 全ルールが悪例で失敗し、良例を通す |
| 型チェック | 未着手 | | |
| lint | 未着手 | | |
| 単体テスト | 未着手 | | |

技術スタックを決めたら、`check:harness` 等の名前でパッケージの検証コマンドへ入れ、CI（`.github/workflows/harness.yml`）と揃える。

## 段階2：検証

### 導入の順序

1. 最初の利用者向け機能が動いたら、`create-verification-skill` でランタイム検証スキルと機能マップを作る。雛形は `templates/harness/verify-project.md` と `templates/harness/features/`。
2. 機能マップの操作を、エージェントが一つのコマンドで実行できる検証用CLIにまとめる。
3. 状態が3つ以上あるフローは `user-statechart` で利用者視点の状態遷移図を作り、遷移ごとの不変条件をプロパティベーステストへ移す。
4. 下の判断基準に当てはまるフローだけ、モデル検査を検討する。

### プロパティベーステストの対象

| 対象（関数・状態機械） | 性質（どの入力でも成り立つこと） | テストの場所 | 状態 |
|---|---|---|---|

### モデル検査の判断

| フロー | 並行・再試行・時間の要素 | 壊れた時の被害 | テストで届くか | 判断 |
|---|---|---|---|---|

判断の基準は [ハーネス設計](harness.md) の「モデル検査の判断基準」を使う。
