# <アプリ名>の機能マップ

利用者向けの振る舞いを検証するための正本。アプリを操作する前にこの索引を読み、該当する機能ファイルを手順として使う。形は上流の `create-verification-skill/references/feature-map-example/` に合わせ、`maintain-verification-skill` がそのまま監査できるようにする。

## 前提状態

- `<起動先URL・CLI・データディレクトリ>`
- `<投入するシードデータ>`
- 検証の前に [検証手順](../project.md) の Doctor を実行する。
- この検証で起動していないインスタンスは操作しない。

## 操作の決まり

- 各手順は、手順に書いた前提を除き、上の前提状態から始める。
- CSSセレクタやDOMの位置より、ARIAのロールとアクセシブルな名前を使う。
- コマンドは書いた通りに実行する。引用符で囲んだ名前とフラグを変えない。
- 書き込みを伴う操作の後はシードデータを戻す。証拠は消さない。

## 証拠と未到達の報告

- 利用者の操作と、その結果の状態を残す。
- UIの証拠はARIAスナップショットと、アプリだと分かるスクリーンショット。
- CLIの証拠はコマンド、stdout、stderr、終了コード。
- 書き込みの証拠は、保存された値を別の読み取り経路で見たもの。
- 証拠ごとに機能IDと入口を記録する。
- 到達できない経路は、試したコマンドと満たせなかった前提を報告する。別の経路で確かめたことを、その経路の検証済みと書かない。

## 機能ファイルの形

各ファイルはH1の題と、利用者に見える振る舞いを一段落で書く。続けて次の4つのH2をこの順で置く。見出しは上流と同じ英語のまま保ち、本文は日本語で書く。

1. `Sub-features`: 短いIDと、振る舞いを1行ずつ。
2. `How to get to it (user POV)`: 利用者のすべての入口。
3. `Driving it with <道具>`: `Preconditions:` から始め、利用者の操作・実行するコマンド・観測できる結果を組にする。
4. `Gotchas`: 検証を無駄にする、または無効にする罠。

実装の詳細は書かない。利用者の経路、安定した取っ手、必要な状態、コマンド、観測できる証拠だけを書く。
