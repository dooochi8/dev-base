# user-statechart

利用者が見る状態と、利用者の操作や外部の出来事による遷移を、Mermaid の `stateDiagram-v2` に描く。図は飾りではなく、コードの状態の正本と照合し、遷移ごとの検証と不変条件のテストへつなぐための台帳である。読み手は、その振る舞いが正しいかを判断する人（利用者の代わりに決める人）とする。

構造や呼び出し関係の図は `show-me`、状態の型の設計は `principle-model-the-domain` を使う。TLA+ によるモデル検査は対象外とし、必要な場合は手順8の判断基準で扱う。上流 pstack の `statechart` は未採用で、理由は `docs/pstack-adoption.md` に記録している。

## ガードレール

- 状態名に変数名・型名・関数名を使わない。「保存中」「オフライン、送信待ちあり」のように、利用者に見えるか利用者が気にすることで書く。
- 図に合わせてコードを読み替えない。図とコードが食い違ったら、それは所見として報告する。
- 規則（不変条件）を、図が成り立つように弱めない。
- レビューだけの依頼で、コードや仕様を書き換えない。

## 進め方

1. **対象と読み手を決める。** 一つのフロー（例: ワークアウトの記録、ログイン、同期）に絞る。複数のフローを一枚に詰めない。
2. **状態の正本を探す。** 型、reducer、状態機械、DBの状態列、URLのルートから、状態を決めている場所を特定する。正本がなく、真偽値やフラグが散らばっているなら、その場所を所見に記録する。
3. **状態を利用者の言葉で並べる。** 各状態で、利用者に何が見え、何ができるかを書く。初期・読み込み中・空・成功・失敗・取り消し・再試行・権限なし・オフラインを、該当しないと確かめるまで候補に残す。
4. **遷移を書く。** ラベルは利用者の操作か外部の出来事で書く（「保存を押す」「通信が失敗する」「5分経つ」）。条件付きの遷移は、末尾に `[ ]` で利用者の言葉の条件を付ける。同じ結果になる操作は一本の矢印にまとめる。
5. **規則を書く。** 読み手が合意する規則を、利用者の文で列挙する（例:「保存済みの記録は、取り消すまで一覧に出る」「送信待ちがある間は、ログアウトしても記録は消えない」）。
6. **図を読める大きさにする。** 矢印は20本程度までにする。同じように振る舞う状態をまとめ、読み手が要らない詳細を落とす。規則が壊れる状態と、その状態に至る経路はまとめない。落とした遷移は文書に書く。
7. **コードと照合する。** 各状態にコードの場所、各遷移にハンドラやイベントの場所を書く。次を所見として列挙する。
   - コードにはあるが図にない遷移（隠れた分岐）
   - 図にはあるがコードでは起きない遷移
   - どの遷移でも出られない状態、どこからも入れない状態
   - 規則が壊れうる遷移
8. **検証へつなぐ。**
   - 各遷移を、機能マップ（`verify/features/`）の手順か、E2E・統合テストへ対応させる。対応がない遷移は未検証として残す。
   - 規則は、ランダムな操作列を状態機械へ与えて不変条件を確かめるプロパティベーステストにする。TypeScript なら fast-check の `fc.commands` 等。ファイル名は `*.property.ts` にする。
   - 並行する操作、再試行、時間切れ、複数の利用者や端末が規則に関わる場合は、`docs/harness.md` の「モデル検査の判断基準」で検討する。
9. **保存する。** [雛形](references/template.md) に沿って `docs/statecharts/<フロー名>.md` に保存し、`docs/verification.md` の状態遷移図の行を更新する。

## 報告

- 図（Mermaid のコードブロック）と保存先
- 規則の一覧と、各規則を確かめるテストまたは手順
- 所見（食い違い・到達不能・抜け）と、その根拠のコードの場所
- 未検証の遷移と理由、図で省いた遷移

## 完了条件

- すべての状態と遷移に、コードの場所か「コードにない」という所見がある。
- すべての規則に、確かめるテストか手順、または未検証の理由がある。
- 図のラベルに実装の名前が残っていない。
