# 開発ベース

日常的なコーディング作業のための共通ベース。何でも詳しく指示する巨大スキルではなく、通常の開発で毎回使う判断基準だけを置き、詳しい手順は `references/` に逃がす。

## クイックスタート

1. 変更対象のコード経路を先に探索する。
2. 目的を観測可能な振る舞いとして言い直す。
3. 進捗を証明できる最小の縦切りを選ぶ。
4. 既存パターンに沿って実装する。
5. 必要最小限の方法で検証する。
6. 何を変え、何を確認し、何が未確定かを明示する。

## 基本方針

- 推測よりコードベース上の事実を優先する。
- 実装の形より振る舞いとインターフェースを優先する。
- 大きな段階的書き換えより、小さなエンドツーエンドの一歩を優先する。
- テストは公開インターフェースか安定した境界で行う。
- 浅いヘルパーを増やすより、モジュール境界を深くする方向を優先する。
- ローカルで発見できず、かつ実装判断に本当に効く情報だけをユーザーに確認する。

## ワークフロー

### 1. 位置取り

実際のコード経路をたどる。

- 高速な検索で入口、呼び出し元、既存テストを見つける。
- 変更箇所を決める前に隣接モジュールも読む。
- 今回の仕事が主に実装、バグ修正、リファクタ、設計整理のどれかを見極める。

### 2. 振る舞いを明確にする

目標を観測可能な形で定義する。

- 変更後、ユーザーや呼び出し元やテストは何ができるべきか。
- 今は何が起きていて、それがどう違うのか。
- 制約のうち事実は何で、思い込みは何か。

まだ曖昧なら `references/discovery.md` を読む。

### 3. スライスを選ぶ

必要な層をまたぐ最小の縦切りを選ぶ。

- 機能追加では、まず経路全体が通ることを示す tracer bullet から始める。
- バグ修正では、可能なら先に失敗を再現する。
- リファクタでは、振る舞いを保ったまま継ぎ目を一つずつ変える。

一回で収まらない作業なら `references/slicing.md` を読む。

### 4. 適切な深さで作る

- 振る舞いを具体的に定義できるなら `references/tdd.md` に従う。
- コードベースが追いづらい、またはテストしづらいなら `references/architecture.md` を読む。
- 実装前に短い整理メモが必要なら `references/prd-lite.md` を使う。

### 5. 検証する

最小で十分な検証を行う。

- 変更経路に対する対象テスト
- 必要に応じた型チェックや lint
- 自動検証がない、または高コストな場合だけ手動確認

実際に確認していないことまで自信ありとは言わない。

## リファレンスマップ

- `references/discovery.md`: 曖昧な依頼や設計案を、空回りせずに詰める方法
- `references/slicing.md`: 作業を薄い縦切りへ分解する方法
- `references/tdd.md`: 境界重視の red-green-refactor
- `references/architecture.md`: deep module を軸にした設計改善
- `references/prd-lite.md`: 非自明な変更のための短い実装整理テンプレート

## ガードレール

- 薄い経路で進捗を示せるのに、最初から大規模書き換えを始めない。
- 最初の実装スライスがない段階で大量のテストを書かない。
- 主たる振る舞いを追いづらくするほど局所的な純粋性を優先しない。
- 今回の作業に役立たない文書化、チケット化、抽象化を増やさない。
