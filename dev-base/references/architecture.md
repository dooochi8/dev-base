# アーキテクチャ

コードが追いづらい、変更に弱い、またはテストしづらいときに使う。

## 主眼

浅いヘルパーの網を広げるより、deep module を作ることを優先する。

deep module は、大きな複雑さを小さく安定したインターフェースの内側に隠す。これにより認知負荷が下がり、テストしやすくなり、将来の変更の置き場も明確になる。

## 摩擦の兆候

- 一つの振る舞いを理解するのに、小さなファイルを何個も飛び回る必要がある。
- モジュールの公開面が実装と同じくらい複雑である。
- テストしやすさのために分割したはずのヘルパーが増えたが、本当のリスクはその連携部にある。
- 小さな変更でも強く結合した複数モジュールにまたがる。

## リファクタ方針

1. 複数のファイルや呼び出し箇所に散っている概念を見つける。
2. 呼び出し側が本来ほしい単純な境界を見つける。
3. 複雑さをその境界の内側へ押し込む。
4. 継ぎ目ごとのテストを、可能なら境界テストへ置き換える。
5. 明示的に挙動変更が求められていない限り、リファクタは振る舞い保存で進める。

## 設計上の問い

- 呼び出し側は何を気にしなくてよくなるべきか。
- 実用上必要な最小のインターフェースは何か。
- どの依存を外に残し、どこまでを吸収すべきか。

## 注意

フレームワーク的な抽象層を増やすこと自体を目的にしない。必要なのは層の追加ではなく、現実の利用者にとって単純な境界である。
