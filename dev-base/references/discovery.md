# 発見と確認

依頼が曖昧、要件が不足している、思い込みのまま実装すると危険、という場面で使う。

## 目的

だらだら質問を増やさずに、変更すべき振る舞いについて具体的で共有可能な理解に到達する。

## 進め方

1. まずコードベースから自力で分かる事実を拾う。
2. 実装判断を変える次の一問だけを聞く。
3. 質問は一度に一つを基本にする。
4. 各質問には現時点での推奨案も添える。
5. 依存関係のある論点を先に潰し、横に広がりすぎない。

## 良い質問

- 呼び出し元やユーザー視点で、何の振る舞いを変えたいのか。
- 既存のどのフローが最も近いのか。
- 新機能なのか、既存挙動の修正なのか。
- 最初のスライスで本当に扱うべきエッジケースはどれか。

## 打ち切り条件

次の状態になったら質問をやめて作り始める。

- 変更後の振る舞いが観測可能な形で言える。
- 関連するコード経路が特定できている。
- 最初の薄いスライスが十分に見えている。
